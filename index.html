The hard problem

This is not an expert-only panel. Discovery marketplace and operations live on the same data model. A member is tied to one live expert at a time. Request approval is locked inside a transaction with SELECT FOR UPDATE. A second expert gets 409 MEMBER_HAS_ACTIVE_EXPERT. A library template is deep-cloned onto the member. Catalog exercises are shared. A package ends on date only. Running out of sessions does not expire it. Key decisions

No external migration tool. Numbered SQL at boot plus _fitsync_migrations. Each file is one transaction.

No Stripe or İyzico for member-expert money. Snapshot price plus subscription_payments, remaining via SUM. Default currency TRY.

Chat writes over REST. An open screen uses one-way WebSocket. Fan-out is an in-process Map (single-instance note in the code). Conversation UUID pair is unique with user_id_a < user_id_b.

Push is not fire-and-forget. A notifications outbox row, minute dispatch cron. Tests do not call FCM, Resend, or S3.

Discover does not look at platform subscription. Active onboarded experts with a published price. Rank: 0.6 conversion count + 0.4 conversion recency (365/180 days).

Repository-specific contribution rules, review expectations, testing requirements, and workflows are difficult to discover and apply consistently. Generic coding rules miss the conventions that make a particular codebase maintainable.

Express Tracing CLI
09 — Developer tools · Observability · Express 5
What it is

A live terminal tracer for Express 5. Run a collector, attach a reporter, and watch requests, middleware timelines, and logs in a three-pane TUI. The instrumentation layer lives separately in express-emits, so measurement and presentation stay independent.

The problem

Express middleware is often a black box during local development. When a request is slow or incorrect, it is difficult to see which middleware ran, in what order, how long each one took, or which log line belongs to that request. Full APM and OpenTelemetry setups are too heavy for this kind of feedback loop.

Two packages, split on purpose

express-emits instruments the app by wrapping app.use and emitting typed start/end events with real durations. express-trace-cli consumes those events, batches them over HTTP to a local collector, and renders sessions, requests, middleware trees, and logs in Ink. If the CLI is not running, events are dropped: this is a development tool, not a durable pipeline.

Technical implementation
ComponentTechnologyPurpose
InstrumentationNode.js EventEmitterTyped request, middleware, and log events
CLI / TUIInk · ReactThree-pane live terminal interface
RuntimeTypeScript · Express 5Express-compatible tracing semantics
TransportHTTP · 200ms batchingFire-and-forget local event delivery
TestingNode test runner · autocannonSemantic guarantees and overhead measurement
Correct timing semantics

Request timing ends on res finish or close, not when next() returns. Middleware duration is self-time until handoff, not the downstream chain. Every middleware.start has exactly one end event, including sync throws, rejected async middleware, and early responses.

Yelix
11 — Framework · 🥇 National award · Open source
The hard problem

Every Deno web framework I found was a Node.js port — they worked against the runtime instead of with it. Deno has native TypeScript, Web platform APIs, and a granular permission system. None of the existing frameworks actually used these. I wanted a framework where Deno's design decisions were features, not obstacles.

Key decisions

Built on Deno's native HTTP server — not a compatibility layer. Uses standard Web API Request and Response objects throughout, which means any knowledge of Fetch API transfers directly.

TypeScript inference over decorators — kept the API surface small and avoided the magic that makes debugging painful. Route types are inferred, not declared separately.
