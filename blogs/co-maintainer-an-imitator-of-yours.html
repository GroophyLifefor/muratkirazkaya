co-maintainer,
an imitator of yours

Every repository holds knowledge nobody wrote down. It lives in whoever has reviewed every pull request for three years, and it leaves when they do.

Murat Kirazkaya 6 min read on context, not models
01 · the repetition

You have written this comment before

Three pull requests, six months apart, three contributors. The same comment every time, worded a little differently every time. The rule is real and everyone knows it. It is just nowhere a machine can read it.

02 · the gap

What the diff does not say

A reviewer reads the patch while quietly holding four years of this codebase. Here is what that is worth.

The types compile, because a branded number is still a number. The fee comes out fractional, ledger.post() asserts integers, and the refund throws on the first amount that does not divide evenly.

A missed finding is usually a missing input, not a weak model.

03 · the reading

Read the repository once, not once per review

Handing the model a whole repository on every review is possible, and absurd. So the reading happens once, off to the side, and what comes out is small enough to carry.

probe

Start with the part that costs nothing

It reads the repository through the GitHub API and prints the init line you should run, limits already filled in. No model is called, nothing is written.

init · extract

A cheap model turns the repository into evidence

Tree, files, pull requests, their diffs, the discussions on them, commit history. Every observation stays bound to the file or pull request that produced it, because a rule nobody can trace back is how a review tool starts inventing them.

init · synthesise

A reasoning model turns evidence into three guides

How to contribute here, how the code is actually written, and what reviewers here have historically stopped pull requests for. They land in your config directory, not in the clone, so a fresh checkout keeps them.

remake

Then keep it alive for the price of a diff

It refetches, reuses every piece of evidence the cache says is unchanged, and rewrites only the guides the new commits touch. init is the once. This is the loop.

04 · the artifact

The guides are the product

Models are rented. Whichever one is best this quarter will not be best next quarter. The context is the part you own.

Read them out loud and they sound like the person who has been merging into this repository for two years. That is where the title comes from. It is not trying to be a better reviewer than your team, it is trying to be a cheap imitation of the one you already have, awake at 2am, on the boring pull requests too.

05 · the review

What it writes on the diff

A pull request opens. The guides are already on disk, so the reviewer starts from a repository it has read instead of a patch it has never seen.

Without the guides there are two honest options here. Say nothing, because a percentage fee is a normal thing to write. Or say something vague about floating point, which everybody has learned to scroll past.

  • Findings carry over. Push a fix, run it again, and the finding closes instead of being raised twice.
  • A blocking finding exits non zero. That is all CI needs.
  • --json on stdout, logs on stderr. Findings, counts, tokens, duration, codegraph state, one document.
  • Codegraph is optional. On by default, and the binary is installed on request, not behind your back.
06 · the three doors

Same guides, three ways in

There are only three answers people actually want: the mess in my working tree, that pull request over there, and the first one without making every laptop pay for init.

07 · remote

Use shared context without running init on your machine

Somebody joins on Monday and clones the repository. Local review wants guides, guides want init, and init wants minutes and money. Paying that once per laptop is how a tool dies in its third week.

The boring safety bits. Tokens are hashed at rest, and deactivating one cancels every review in flight for it. The CLI prints a one time notice per host the first time it uploads a diff, so nobody finds out by reading the source six months later.

08 · the server

When you want the boring half automated

co-maintainer serve is one process and one app.db. It carries the GitHub App webhook, a job worker, the dashboard, and the remote review API from the last act.

Add a repository and init runs as a job you can watch. Flip auto review on and a pull request opening is enough to start one. The repo above has been connected for 8 days. Everything, init, remake and every review included, cost $1.20 in total.

09 · the evidence

Does any of this actually work

Thirty pull requests on a repository of mine. Fourteen carry a deliberately seeded, hand verified defect. Sixteen are clean controls, which is the part most review benchmarks skip and the part that makes precision measurable.

Every defect that needed something outside the diff was caught. The two misses are on the axes where everything needed was already sitting in the patch, which is funny and slightly humbling: the context machinery works, ordinary close range reading is what still slips.

Thirty pull requests, no repeat runs, so variance is unmeasured. It raises about one unnecessary finding per clean pull request, and that number is what decides whether a team keeps a review bot or mutes it.

10 · the point

Context optimisation is not a loss of yield

The question was never which model reviews best. Models change every few months and the answer expires with them. The question is what the model is holding when it starts. Giving it more context does not make the prediction more accurate.
